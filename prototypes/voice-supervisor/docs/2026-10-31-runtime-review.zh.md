# 语音 Agent 原型运行评审（2026-10-31）

本次按用户要求核对真实语音会话、模型配置、持久化模型流和主子代理消息链。统计窗口为北京时间 14:11:19～14:15:49 接收的 8 次真实语音输入；排除此前的合成集成测试与直接工具检查。原始对话、录音、文件名及会话标识留在本地忽略目录，本报告只记录匿名汇总。运行时未重启，模型、提示词与固件未变更。

## 1. 接话为什么生硬

实际前台接话、主调度器、所核对的执行子代理均为云端 deepseek-flash，关闭思考。证据是运行 trace 的 front.request/front.reply、scheduler.request，以及父子会话 assistant/message 的模型来源，不只是配置默认值。接话使用官方 chat/completions 入口，主调度走 Harness 配置的官方 Anthropic 兼容入口；模型名称一致不表示两条请求链、上下文与协议完全一致。

接话层只接收本轮文本；提示词限制一句 8～20 字，不回答实质内容、不提问，并给出“收到……”范例。max_tokens=64 是输出上限，不是模型参数量。8 次接话文本互不相同，不能说模型一直在重复完全相同的话；但提示词强制确认式风格、缺少对话背景，确实限制了可表达范围。提示词是生硬感的合理原因，尚未通过 A/B 证明，更不能据此断定模型参数太少。

语言模型不在本机运行；本地的是 ASR。当前没有独立前台小模型/后台大模型的规模配置。换云端模型须修改模型选择并核对可用性；增加输出 token 上限不会增加参数量。建议先改提示词、加精简上下文再比较自然度与延迟，不直接更换更贵模型。

## 2. 实际延迟与口径

起点统一取 input.accepted；接话 TTFT 则采用该 HTTP 请求自身计时。主调度首输出从原生 assistant/message.stream 恢复，首 token 可以是工具调用，不能直接朗读。第一段文字从第一个非空白文字增量恢复；完整回复采用第一个含文字的 assistant/message 持久化时刻。工具耗时会影响后两项。

| U2 | 14:11:39.449 | 0.646s | 0.698s | 0.698s | 1.167s | 无 |

| U5 | 14:13:22.855 | 0.707s | 1.234s | 1.234s | 1.335s | 无 |

接话 TTFT 为 0.302～0.759 秒，中位数约 0.583 秒；完整接话文本为 0.476～0.902 秒。主调度首模型输出为 0.698～1.508 秒，中位数约 0.899 秒；首次完整文字为 1.167～25.002 秒，中位数 3.269 秒。存在明显的完整文字回复波动，但本组样本不呈现逐轮持续变慢的趋势。

不能把主调度首模型输出上述数值称为精确 API TTFT：起点包含入口、调度与上下文处理。旧日志可以算出 step/start → 首 token 为 0.541～1.103 秒，中位数约 0.702 秒，但步骤起点也早于真正请求发起。原型未保存每次 HTTP/提供方请求发起时间，因而无法严格追溯 API TTFT 或单独归因网络、提供方与本地准备时间。

U3、U4、U6、U8 的首输出均先是工具调用；文字出现较晚。其中 U8 首模型输出只用了 0.863 秒，但第一段可见文字在 23.180 秒出现、完整文字在 25.002 秒出现；该轮先写文件、再呈现文件。进一步核对发现，该次 write 参数长 11,758 字符，从首个工具 token 到这次参数生成完成约 20.3 秒；实际 write 调用到返回只有约 30 毫秒，present 调用到返回约 6 毫秒。因此主要等待发生在生成整份文件内容的工具参数阶段，不能归因于磁盘写入慢。这组证据更支持“先做工具工作、再形成完整回答造成体感等待”，不支持单纯以模型 TTFT 波动解释全部等待。

当前工作台“首次完整回复”标签与实现相符；应增加真正的首输出、首文字和 API TTFT 独立指标。文字生成、TTS 就绪、设备出声和音频播放完成须各自计时；本表没有把文本延迟当成语音出声延迟。

子代理执行了 6 次 web_search 和 15 次 web_fetch。这里确认的是执行、结果进入主上下文、主调度生成汇总及后续文件存在；没有对报告每条外部事实重新进行独立审计，也不把原生 completed 等同于内容必然准确。

这次结果没有走显式 send_message，而是 Harness 的自动结束通知 subagent-settled。当前 trace.mjs 只将 source.kind=agent-message 投影成 child.relay，遗漏结束通知。所以上下文已收到结果，但工作台只显示“子代理结束”，容易让人误以为没有回传。这是观测缺口，并非此次后端回传失败。

还发现声音送达的并发缺口：用户在 14:15:33.849 开始下一次录音，早于子任务结束；原任务汇总归属旧 requestId，新一轮语音桥只读取新 requestId 的消息。该 524 字符汇总有 scheduler.reply 日志，但没有对应 audio.released、TTS 或设备播放完成证据。主调度随后却声称刚才已口头汇报。生成汇总不等于用户听到，这正是需要优先修复的体验问题。

## 4. 改造优先级

1. P0：工作台同时呈现主动 agent-message 和自动 subagent-settled，保留子运行结果与父会话接收两个独立状态。
2. P0：后台结果使用独立的持久待汇报队列；任务归属和当前播放周期分开。旧录音轮次取消后，结果仍可由当前主调度组织并播出。没有设备 ACK 时，主调度不得认定已口头告知。
3. P1：接话提示词与精简对话上下文 A/B；拆分前台、主调度和执行模型配置。先验证自然度，再考虑模型切换。
4. P1：增加每次模型调用的准确开始时间、首文字/首工具 token 与完成事件，并拆分工具、TTS 和播放等待。短工具先说明、长工作委派，并验证自身工具执行期间的响应能力。

具体数据流和验收要求见 PRD v0.4 第 22 节。本次完成诊断和文档更新；上述运行逻辑与提示词的修改尚未实施，避免在用户测试中重建当前主会话。
