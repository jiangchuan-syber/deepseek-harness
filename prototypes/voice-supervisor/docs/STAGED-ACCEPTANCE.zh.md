# 分阶段语音调度改造与验收（2026-10-31）

PRD 先更新至 v0.5，再实施工程改造。原生主会话、既有隔离 home 和工作目录保留；现用服务继续使用原主会话 ID。原生会话恢复采用 resolveAgent，不能把 create(sessionId) 当作恢复已有对话的 API，后者可能新建会话。未修改已安装桌面版，未刷写 ESP32 固件。

## 运行行为

- 交互运行器取消独立接话 API 请求。同一个 Harness 主会话先以 off 接话，快速阶段工具声明为空，并由执行门禁拒绝工具执行；快速回应作为 assistant 消息留在原上下文。
- 应用内部 voice-continuation 事件触发 high 深度处理，原始用户话语只提交一次。耗时研究和执行按需委派原生子代理，结果返回主上下文后由主调度整理。
- 主调度串行运行，快速输入优先于尚未开始的深度续接，多个待续接可合并。已经运行的深度请求期间，新输入显示排队；未实现即时抢占。
- 工作台显示快速回应、正在思考中、工具执行中、等待子代理，以及排队输入条数；模型流只暴露计时与增量类别，不显示内部思考正文。接话首字计时从原生流开始至首文字增量，不冒充网络层精确 API TTFT。
- agent-message 与 subagent-settled 两种回传均可观察。任务归属与声音送达分别记录，旧未播结果在后续输入中交给主调度重新组织，不自动重播。
- 每条原生消息带 messageId，每个真实音频片段带序号与片段总数。全部片段获得真实完成 ACK 后才确认整条消息送达；打断段位置仍未知。只有快速回应而无需补充的轮次也能正常结束，不永久占用设备。
- 阶段接纳、处理和送达事实保存在 phase-queue.jsonl；生成语音保存在 speech-outbox.jsonl，原生模型历史保存在 Harness 会话。重启不自动重放未知是否完成的任务。

隔离样本的两次快速回应，从原生流开始到首文字增量分别约 875 / 563 毫秒，完整文本约 1112 / 756 毫秒。开发板任务示例一次接话首字约 609 毫秒，完整文本约 773 毫秒。样本很少，不是稳定性或百分位保证。

物理链路验收使用文字注入，跳过录音与 ASR；不能据此宣称重新验证了人声识别质量或实物按键打断。界面观察到真实“正在思考中”状态，并保存了子任务运行中的工作台截图。

## 已知边界

深度推理中的新输入先排队，不能瞬时回答。完整任务暂停仍由主调度通过 Harness 工具执行。当前未实现崩溃后自动任务重放、空录音后自主送达、打断段的精确采样位置，也不保证模型永远正确判断某条旧结果是否应重新播报；这些能力不能用状态标签代替验收。
